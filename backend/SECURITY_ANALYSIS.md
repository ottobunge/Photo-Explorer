- Null byte injection
- Encoded traversal attempts

## Security Implementation Details

### 1. Multi-Layer Defense Strategy

The security model uses **defense in depth** with multiple validation layers:

#### Layer 1: Source Control (Application Layer)
- Face crop paths are **never directly user-supplied**
- Paths are stored in database and generated by application during photo processing
- Face entities are loaded from persistent storage, not parsed from user input
- See: `app/adapters/inbound/api/routes/faces.py:478` - path comes from `face.crop_path`

#### Layer 2: Port Interface (Application Layer)
- `FileStorage` port defines abstract interface in `app/application/ports/outbound/file_storage.py`
- All file operations must go through this controlled interface
- No framework types leak into domain layer
- Dependency points inward (adapters implement ports)

#### Layer 3: Validation (Adapter Layer)
- Validation happens at the adapter level in `LocalFileStorage`
- `_validate_and_resolve_path()` implements canonical path resolution
- `_resolve_path()` applies validation before attempting filesystem access
- All public methods use validation before filesystem operations

#### Layer 4: Operating System (OS Level)
- Uses Python's `pathlib.Path.resolve()` for canonical form
- Leverages OS-level symlink resolution
- File permissions respected by filesystem

### 2. Validation Algorithm

The security validation uses the following algorithm:

```python
async def get_file(self, path: str) -> Optional[bytes]:
    """Read a file from storage with path traversal protection."""

    # 1. Resolve path in one of three storage directories
    full_path = self._resolve_path(path)

    # 2. Return None if no valid path found
    if not full_path or not full_path.exists():
        return None

    # 3. Read file from validated path
    try:
        async with aiofiles.open(full_path, "rb") as f:
            return await f.read()
    except OSError as e:
        logger.error(f"Error reading file {path}: {e}")
        return None


def _validate_and_resolve_path(
    self, path: str, base_path: Path
) -> Path:
    """Validate and resolve path within allowed base directory.

    Security guarantees:
    - Rejects absolute paths
    - Rejects paths with ".." components
    - Rejects symlinks that escape base directory
    - Verifies final resolved path is within base directory
    """

    # STEP 1: Reject absolute paths
    if os.path.isabs(path):
        raise PathSecurityError(
            "Absolute paths are not allowed",
            attempted_path=path,
        )

    # STEP 2: Reject paths with ".." components
    if ".." in path.split(os.sep):
        raise PathSecurityError(
            "Path traversal with '..' is not allowed",
            attempted_path=path,
        )

    # STEP 3: Construct and resolve to canonical form
    # This resolves symlinks and normalizes path
    full_path = (base_path / path).resolve()

    # STEP 4: Verify resolved path is within base directory
    try:
        full_path.relative_to(base_path.resolve())
    except ValueError:
        raise PathSecurityError(
            f"Path escapes allowed directory: {path}",
            attempted_path=path,
        )

    return full_path
```

### 3. Security Guarantees

#### What This Protects Against

| Attack | Mechanism | Status |
|--------|-----------|--------|
| Path traversal | `../../etc/passwd` | Blocked: ".." detection + resolve validation |
| Absolute paths | `/etc/passwd` | Blocked: `os.path.isabs()` check |
| Symlink escape | Symlink to `/etc` | Blocked: `resolve()` validates canonical path |
| Null bytes | `file\x00.txt` | Blocked: Python path handling rejects |
| Mixed encoding | URL-decoded `%2e%2e` | Blocked: Operates on decoded path |
| Case variation | `..` as `%2E%2E` then decoded | Blocked: Validated after decoding |

#### What This Does NOT Protect Against

| Scenario | Reason | Mitigation |
|----------|--------|-----------|
| User-supplied filenames on save | Application pre-sanitizes at `save_photo()` | `_sanitize_filename()` removes traversal chars |
| External source paths | Paths from connectors assumed trusted | TODO: Validate registered connector folders |
| Time-of-check/time-of-use | Race condition on filesystem | Rare in practice; mitigated by file permissions |
| Filesystem access control errors | Misconfigured permissions | Outside application scope; OS responsibility |

```python
async def delete_file(self, path: str) -> bool:
    """Delete a file from storage."""
    full_path = self._resolve_path(path)  # <-- VALIDATION

    if not full_path or not full_path.exists():
        return False

    try:
        await aiofiles.os.remove(full_path)
        logger.debug(f"Deleted file {path}")
        return True
    except OSError as e:
        logger.error(f"Error deleting file {path}: {e}")
        return False
```

## Threat Model Analysis

### Attack Vectors Considered

#### 1. Direct User Input Attack
**Scenario**: User provides path directly in API request
**Status**: NOT APPLICABLE
- Reason: Paths are stored in database, not parsed from user input
- Endpoint `/api/v1/faces/{face_id}/crop` uses face_id UUID
- Crop path retrieved from database entity
- **No user-supplied paths exposed to filesystem operations**

#### 2. Database Injection Attack
**Scenario**: Attacker modifies database to insert malicious path
**Status**: MITIGATED BY VALIDATION
- Even if database is compromised, path validation occurs at adapter layer
- Invalid paths are rejected before filesystem access
- Validation is independent of path source

#### 3. Symlink Planting Attack
**Scenario**: Attacker places symlink in storage directory pointing to system files
**Status**: PROTECTED
- Path validation resolves symlinks to canonical form
- Canonical path must be within base directory
- Symlinks cannot escape storage hierarchy

#### 4. Null Byte Injection
**Scenario**: Attacker includes null bytes in path (`file\x00.txt`)
**Status**: PROTECTED
- Python's pathlib automatically rejects null bytes
- OS-level path handling enforces this
- No special handling needed

#### 5. Filename Encoding Attacks
**Scenario**: Attacker uses URL encoding, UTF-8 encoding, or other tricks
**Status**: PROTECTED (with caveats)
- Path is validated after decoding
- Canonical form normalization resolves encoding tricks
- Note: Responsibility to decode paths at API boundary (FastAPI handles this)

#### 6. Time-of-Check/Time-of-Use (TOCTOU)
**Scenario**: File is modified between validation and reading
**Status**: ACCEPTED RISK
- Validation occurs immediately before filesystem access
- Race condition window is minimal (microseconds)
- Mitigated by OS file permissions
- Rare in practice; trade-off for simplicity

## Security Boundary Documentation

### What Is Trusted

1. **Database content** - Paths stored in database are assumed to be valid
   - Rationale: Database is controlled by application
   - Assumption: Database access is restricted
   - Validation: Still validated at adapter layer as defense-in-depth

2. **Configuration paths** - Storage base directories are from configuration
   - Rationale: Configuration controlled by system administrator
   - Assumption: Config files are read-only
   - Validation: Base paths must be absolute and exist on startup

3. **Framework parsing** - FastAPI request parsing is trusted
   - Rationale: FastAPI is widely-used, well-maintained framework
   - Assumption: Framework correctly parses and validates input
   - Note: We still validate paths independently

### What Is NOT Trusted

1. **User-supplied paths** - Never accepted directly from API requests
   - Exception: UUIDs for entity IDs (numeric/hex only)
   - All filesystem paths come from database

2. **Third-party libraries** - File I/O operations validated
   - Example: `aiofiles` is used but path validation is independent
   - Principle: Defense-in-depth

3. **Filesystem state** - Paths validated before filesystem operations
   - Symlink contents not assumed safe
   - Permissions delegated to OS level
